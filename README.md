# Task Tracker API

REST API для модуля трекера задач медицинской информационной системы (МИС).

## Стек

- Ruby 3.4.1
- Rails 7.2 (API mode)
- PostgreSQL 16
- RSpec + rswag (TDD + Swagger docs)
- Blueprinter (сериализация)
- Docker + Docker Compose

---

## Запуск через Docker (рекомендуется)

```bash
# Клонировать репозиторий
git clone <repo-url>
cd task_tracker

# Запустить
docker compose up --build

# В отдельном терминале — создать БД и применить миграции
# (системные теги создаются автоматически последней миграцией)
docker compose exec web bundle exec rails db:create db:migrate
```

Приложение доступно на `http://localhost:3000`.
Swagger UI: `http://localhost:3000/api-docs`

## Локальный запуск (без Docker)

### Требования
- Ruby 3.4.1
- PostgreSQL 16+

### Установка

```bash
bundle install
```

### Конфигурация БД

По умолчанию подключение через Unix socket без пароля (подходит для большинства локальных установок).
Для настройки через TCP используйте переменные окружения:

```bash
export DB_HOST=localhost
export DB_USERNAME=your_user
export DB_PASSWORD=your_password
```

### Создание БД и миграции

```bash
bundle exec rails db:create db:migrate
```

Системные теги (`отчетность`, `операции`, `звонок`) создаются автоматически при `db:migrate`.

### Запуск сервера

```bash
bundle exec rails server
```

## Архитектурные решения

### Повторяющиеся задачи (Recurrence)

**Проблема бесконечности решена через "генерацию на лету":**
- В БД хранится только _правило_ повторения (`recurrence_type` + `recurrence_params` в JSONB).
- При запросе `GET /api/v1/occurrences?date_from=X&date_to=Y` сервис `Occurrences::ListService`
  генерирует даты для каждой периодической задачи прямо в памяти — без предзаписи в БД.
- Максимальный диапазон запроса — **366 дней**. Более широкий диапазон возвращает `400 Bad Request`.

**Независимое состояние экземпляров:**
- Таблица `task_occurrences` — _sparse_ хранилище переопределений. Запись создаётся только
  когда конкретный экземпляр был явно изменён (смена статуса, отмена, изменение заголовка).
- Все остальные экземпляры неявно имеют статус `pending` и данные из шаблона задачи.
- `PATCH /api/v1/tasks/:task_id/occurrences/:date` создаёт или обновляет запись в `task_occurrences`
  только для указанной даты — остальные экземпляры не затрагиваются. Дата валидируется
  по правилу периодичности (для recurring) или против `due_date` (для one-time); попытка
  патчить дату вне расписания возвращает `422 Unprocessable Entity`.
- `cancelled: true` без явного `status` автоматически выставляет `status = "cancelled"`;
  комбинация `cancelled: true` + ненулевой/не-`cancelled` статус отклоняется (`422`).
- Уникальный ID `task_occurrences.id` присутствует только для записей с override.
  Стабильный составной ключ экземпляра — `(task_id, occurrence_date)`.
- `DELETE /api/v1/tasks/:task_id/occurrences/:date` сбрасывает переопределение и возвращает
  экземпляр к состоянию шаблона.
- Override `title` / `description` различает `null` (нет переопределения, берётся значение
  шаблона) и пустую строку `""` (явная очистка для конкретного дня).

**"Отрыв" экземпляра от правила:**
- `task_occurrences` хранит `title`, `description`, `cancelled` — можно переопределить
  любое свойство конкретного экземпляра не меняя шаблон.
- Поле `cancelled: true` отменяет один конкретный день, не трогая другие.

**Смена правила периодичности:**
- При изменении `recurrence_type`, `starts_on`, `ends_on`, `recurrence_params` **или `due_date`**
  переопределения (`task_occurrences`) автоматически очищаются:
  - Для периодических задач удаляются только те overrides, чья дата больше не попадает в новое правило.
  - Для одноразовых задач удаляются overrides с датами, не совпадающими с новым `due_date`
    (override на самом `due_date`, если существует, сохраняется).
  - При конвертации периодической задачи в одноразовую: логика одноразовой (см. выше).

### Типы повторений

| `recurrence_type`  | `recurrence_params`                          | Пример                                      |
|--------------------|----------------------------------------------|---------------------------------------------|
| `daily`            | `{ "interval": N }`                          | `{ "interval": 2 }` — каждые 2 дня         |
| `monthly`          | `{ "day": N }`                               | `{ "day": 15 }` — 15-е число каждого месяца |
| `specific_dates`   | `{ "dates": ["YYYY-MM-DD", ...] }`           | конкретные даты                             |
| `even_odd`         | `{ "parity": "even" \| "odd" }`              | `{ "parity": "even" }` — чётные числа      |

Для `monthly` с `day: 31` в коротких месяцах (февраль и т.д.) дата автоматически
сдвигается на последний день месяца.

Все даты в `specific_dates` и во всех параметрах API должны быть в формате **ISO 8601 (`YYYY-MM-DD`)**.
Другие форматы (`DD-MM-YYYY`, `MM/DD/YYYY` и т.д.) возвращают `400 Bad Request`.

Ограничения параметров повтора (анти-DoS):
- `daily.interval`: 1..365
- `specific_dates.dates`: до 366 элементов; дубликаты дедуплицируются.

### Системные теги

Теги `отчетность`, `операции`, `звонок` создаются автоматически при `db:migrate` (data migration).
Попытка удалить или изменить системный тег возвращает `403 Forbidden` / `false` на модельном уровне.
Имена тегов нормализуются к нижнему регистру при сохранении — `"Звонок"` и `"звонок"` — один тег.

### Предположения

1. **Авторизация вынесена за рамки**: API не требует аутентификации (предполагается, что она
   обрабатывается вышестоящим слоем / API Gateway МИС).
2. **Один тип задачи — один экземпляр**: не реализовано разграничение по пользователям (врачам),
   т.к. требования не содержат сущности "пользователь".
3. **Статус шаблона задачи**: для одноразовых задач `status` хранится напрямую в `tasks`
   и возвращается в ответе; для периодических — шаблонный `status` не имеет смысла,
   поэтому `GET /api/v1/tasks` возвращает `"status": null` для recurring задач.
   Реальный статус каждого экземпляра доступен через `GET /api/v1/occurrences`.
4. **Фильтрация `GET /api/v1/tasks`** работает только по `due_date` одноразовых задач.
   Для календарного просмотра с раскрытием периодических задач используйте
   `GET /api/v1/occurrences?date_from=X&date_to=Y`.
5. **Временная зона**: все даты (`occurrence_date`, `due_date`, `starts_on`, `ends_on`) хранятся
   как `Date` без привязки к TZ. Клиент обязан передавать дату в своей временной зоне.
